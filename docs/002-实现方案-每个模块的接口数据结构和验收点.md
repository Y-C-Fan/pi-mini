# pi-mini 完整实现方案

一句话：从零到能跑的一份规格书——环境、分层、数据形状、七个模块的接口与边界、写码顺序、验收用例、已知坑。不含实现代码，代码你自己写。
什么时候读：开工前整篇读一遍；之后每写一个模块，只重读对应小节。
层级：002，上级入口 README.md（000）；阶段划分见 PLAN.md（001）。

## 0 目标与完成标准

范围：P0–P3 必做，即内核 + 会话树 + 压缩；P4 交互模式与 P5 扩展面（REPL、RPC、skills）选做，不进退出的验收。
四条完成标准，缺一条不算做完：
1. `pi-mini -p "读 README 并总结"` 能自主调工具完成，多轮不崩。
2. `pi-mini -c` 能接着上次会话继续，模型看得到历史。
3. 同一会话文件里存在两条分支，切换后模型看到的上下文不同。
4. 30 轮长任务触发一次压缩后仍能继续，且旧记录一条没丢。

## 1 环境与骨架

Python ≥ 3.11，包管理用 uv，运行时零依赖（标准库够）。
骨架已在仓库里：`pyproject.toml`（hatchling + `[project.scripts] pi-mini`）、`src/pi_mini/`、`.env.example`。
跑法：`uv sync` 之后 `uv run pi-mini ...`；测试只加 `pytest` 作为 dev 依赖。

配置三级覆盖，优先级 CLI 参数 > `.env` > `~/.pi-mini/config.json`：
`PI_MINI_BASE_URL`、`PI_MINI_API_KEY`、`PI_MINI_MODEL`、`PI_MINI_CONTEXT_WINDOW`（默认 128000）。

## 2 分层与依赖方向

单向：`modes → agent → session → ai`，`agent → tools`。
session 不知道 agent 存在；ai 不认识工具；tools 不 import agent。
出现反向 import 就是设计错了，先改结构再加功能。

## 3 数据结构（动笔前抄一遍，全程不改形状）

### 3.1 会话文件

路径 `~/.pi-mini/sessions/<id>.jsonl`，一行一条 JSON，UTF-8，只追加。自定 `version: 1`，只放本方案的字段子集。

首行仅一次：
```
{"type":"session","version":1,"id":"<uuid>","cwd":"<abs>","model":"<name>","createdAt":"<ISO8601>"}
```

消息 entry：
```
{"id":"<8hex>","parentId":"<8hex>|null","timestamp":"<ISO8601>","type":"message",
 "message":{"role":"user|assistant|system","content":[...]}}
```
`content` 用 OpenAI 形状：
- 文本 `{"type":"text","text":"..."}`
- assistant 的调用 `{"type":"toolCall","id":"call_x","name":"read","arguments":{...}}`
- 工具结果 `{"type":"toolResult","toolCallId":"call_x","output":"...","isError":false}`

压缩 entry：
```
{"id":"...","parentId":"...","timestamp":"...","type":"compaction",
 "summary":"<六段纯文本>","firstKeptEntryId":"<8hex>","tokensBefore":12345}
```

### 3.2 工具表（进程内，不落盘）

`TOOLS = {name: {"description": str, "parameters": <JSON Schema>, "run": callable}}`
`run` 返回 `{"output": str, "isError": bool}`，不向上抛异常。

### 3.3 事件（内存流，永不落盘）

七类，字段固定：
- `turn_start {turn:int}`
- `text_delta {text:str}`
- `tool_call {id,name,arguments}`
- `tool_result {id,output,isError}`
- `usage {inputTokens,outputTokens}`
- `done {reason:"stop|max_turns|aborted|error"}`
- `error {message}`

判定标准：entry 是持久真相，event 是瞬时通道。把事件写进会话文件、或让 entry 出现在事件里，都是错的。

## 4 模块规格

### 4.1 ai/client.py —— 唯一懂 HTTP 与 SSE 的地方

接口 `stream_chat(model, messages, tools) -> Iterator[Event]`。

必须自己处理：
1. 按 `\n` 切行并维护缓冲，跨 packet 残行留到下次拼接（SSE 不保证一次 recv 出整行）。
2. 空行是帧分隔，`data: [DONE]` 是结束。
3. `choices[0].delta.content` 直接产 `text_delta`。
4. `delta.tool_calls` 是分片：按 `index` 归并，`id`/`name` 只在首片出现，`arguments` 是字符串碎片顺序拼接，流结束才 `json.loads`。一次响应可有多个调用，分片会交错。
5. 末帧可能带 `usage`；没有就按 4.5 的估法自己算。
6. HTTP 非 200 先读 body 再报错，错误体一般是 JSON，把 message 提出来。

边界：超时 120s；服务端直接返回 JSON（非 SSE）当错误；空 `choices` 跳过；`finish_reason` 记到本轮结果上，循环要用。
不做：重试、多 provider、图片、流式增量解析。

验收（fixture 回放，不走网络）：三段文本 + 一个两片的 tool_call，断言 3 个 `text_delta`、1 个 `tool_call`、arguments 是完整 dict、`done.reason == "stop"`。

### 4.2 tools/ —— 四个工具 + 注册表

- `read(path, offset?, limit?)`：2000 行或 50KB 先到为准；超限追加 `[Showing lines a-b of N. Use offset=X to continue.]`；单行超 50KB 单独提示。
- `write(path, content)`：自动建父目录，返回 `Successfully wrote to <path>`。
- `edit(path, edits:[{oldText,newText}])`：oldText 必须在原文唯一且互不重叠；不唯一就失败并回错误文本，不许猜。
- `bash(command, timeout?)`：`subprocess` 跑 shell，显式给 cwd 与 shell；超时杀掉进程组；stdout+stderr 取尾部 2000 行/50KB，截断时把完整输出写临时文件、结果里给路径；exitCode≠0 即 `isError`。

路径安全：相对路径按进程 cwd 解析，拒绝 `..` 越出 cwd。
参数校验按宽松口径：数字字符串转数字，单值包成单元素数组；报错一行一条，形如 `- path: missing`。

验收：edit 遇非唯一文本返回错误；bash 超时返回错误而不是挂死；read 大文件带续读提示；write 之后能立刻 read 回来。

### 4.3 agent/loop.py —— 唯一知道"要不要再来一轮"的地方

接口 `run(messages, tools) -> Iterator[Event]`。

循环规则：
1. 一轮 = 一次请求 + 执行该响应里的全部工具调用。
2. 再来一轮的条件：本轮有 tool_call，或队列里有待发消息。都没有就 `done{stop}`。
3. 工具串行执行，逐个产 `tool_call` 与 `tool_result`。
4. 工具失败不抛：转成 `{"output":"Error: ...","isError":true}` 回喂。
5. `finish_reason == "length"` 时该响应的 tools 一个都不执行，全部回错误。
6. 安全阀 `max_turns` 默认 32，到就 `done{max_turns}`。
7. abort 标志每轮开头检查，置位就 `done{aborted}`，已产生的历史不删。

最容易写错的地方：assistant 带 tool_calls 的那条消息必须原样回传，后面紧跟 `toolCallId` 对得上的工具结果消息。顺序错了或改了内容，OpenAI 兼容端点直接 400。

验收四条：单轮无工具；一轮两个工具；工具抛错后模型收到 `isError` 文本并自我纠正；`max_turns` 命中时干净退出。

### 4.4 session/store.py —— JSONL 树的读写与重建

接口：`append(entry)`、`entries()`、`leaf()`、`set_leaf(id)`、`build_context(leaf_id)`、`fork(from_id)`、`list_sessions()`。

规则：
1. `append` 先写盘成功并 flush，再更新内存 leaf。写盘失败不许留孤儿 entry，否则 parentId 指向空洞。
2. 读到半行（进程被杀）就跳过，别把整个文件判废。
3. `build_context`：从 leaf 沿 parentId 逆走到 root，反转成正序，转成模型消息。
4. 路径含 compaction 时：取最新那条的 summary 当第一条，跳过它之前的 message，从 `firstKeptEntryId` 起取到 compaction 前，再接 compaction 之后的全部。
5. 分支靠 leaf 指针切换，不复制数据；`fork` 只写新 session 头 + 复制到分叉点的 entry。

验收：写两条分支切 leaf 后 `build_context` 内容不同；压缩后消息条数下降而文件行数不变。

### 4.4.1 entry → 模型消息的转换

`build_context` 的产物必须是 OpenAI 形状的消息数组，逐条按下表转：

- `message(role=user)`：原样一条 `{"role":"user","content":"..."}`。
- `message(role=assistant)` 纯文本：一条 `{"role":"assistant","content":"<拼接后的文本>"}`。
- assistant 里的 `toolCall` 块：并入同一条 assistant 消息的 `tool_calls`，元素形状 `{"id":"call_x","type":"function","function":{"name":"read","arguments":"<JSON 字符串>"}}`。注意 `arguments` 是字符串，不是对象。
- `toolResult` 块：单独一条 `{"role":"tool","tool_call_id":"call_x","content":"<output>"}`；`isError` 为真时正文前缀 `Error: `。
- `compaction`：转成一条摘要消息（`role:"user"`），放在结果数组第一位，替换掉它之前的所有 message。
- `message(role=system)`：放在结果数组最前，与 §4.6 装配的系统提示是同一条。

顺序硬约束：assistant 的 `tool_calls` 之后，必须紧跟每个 `id` 对应的 `role=tool` 消息，数量与顺序都和 `tool_calls` 数组一致。
缺一条、多一条、顺序颠倒，OpenAI 兼容端点一律 400，且报错信息通常只说 "tool_call_id not found"，不好定位。

### 4.5 session/compaction.py —— 插摘要，不删历史

- 估 token：`ceil(chars/4)`；有真实 usage 回报时，只在回报点之后估算。
- 触发：`估算 > contextWindow − 16384`，或手动 `--compact`。检查时机是工具结果落地后、下次请求前。
- 切点：从尾部往回累计到 20000 token 停止，不切在工具结果中间；单条用户消息就超预算时允许切开，双摘要合并。
- 摘要 prompt 固定六段：Goal / Constraints & Preferences / Progress / Key Decisions / Next Steps / Critical Context。序列化历史时工具结果截到 2000 字符。
- 写一条 compaction entry，`tokensBefore` 记压缩前估算值。

验收：造 30 轮假历史，断言发生一次压缩、message 行数不变、下次请求条数明显下降、压缩后还能继续跑两轮。

### 4.6 context.py —— 系统提示与上下文文件

系统提示不是请求顶层的 system 参数，而是消息列表第一条 `role=system`，按此顺序用空行连接：
preamble（角色与工作方式）→ tools（每工具一句用途）→ rules（工具准则 + 简洁输出）→ project_context → skills（只列 name/description/location）→ cwd。

上下文文件发现：每目录取第一个存在的，先全局 agent 目录，再从仓库根逐级到 cwd，
候选顺序 `AGENTS.override.md → AGENTS.md → AGENTS.MD → CLAUDE.md → CLAUDE.MD`。
包裹格式 `<project_instructions path="...">...</project_instructions>`。

验收：临时目录造 AGENTS.md，断言它按序进了系统消息；关掉上下文文件开关后断言没进。

### 4.7 modes/ —— 同一事件流的三个消费者

- print：只输出 `text_delta` 文本，工具调用打一行短提示，例如 `→ read path`。
- json：一事件一行 JSONL，原样输出，字段不改名。
- （后续）interactive：换渲染器，不许重写 agent。

验收：同一次 run，print 输出的字符与 json 里 `text_delta` 拼接结果一致。

## 5 CLI 表面

`pi-mini [options] [prompt]`：
- `-p/--print <prompt>`：单发
- `--json`：事件 JSONL
- `-c/--continue`：接最近会话
- `-r/--resume <id|path>`、`--list`：接指定会话、列会话
- `--fork <entryId>`：从某条 entry 分叉
- `--compact`：手动压缩一次
- `--max-turns <n>`：安全阀，默认 32
- `--model <name>`、`--base-url <url>`、`--no-context-files`
- `--debug-context`：打印本次请求的消息条数、估算 token、是否压缩过

`--debug-context` 不是可选项。它是你调试上下文工程的唯一窗口，第 5 步之前就要能用。

## 7 与上游的三处有意偏离

1. 加 `--max-turns`：上游靠消息队列与 finishTurn 自然终止，我们没有那套编排，需要硬阀门。
2. 工具串行：上游支持并行并按原序回填，我们单线程够用，省掉并发正确性这一整块。
3. 会话格式自定：我们的 JSONL 是 `version: 1` 的自定义子集，只保留 session / message / compaction 三类 entry；上游是 `version: 3`，有 12 类 entry（model_change、usage、label、branch_summary 等）。pi-mini 的文件不要指望被上游读。

这三条写进 README，别偷偷改。

## 8 自己写必撞的坑

- tool_calls 分片按 `index` 归并，按出现顺序归并会把两次调用粘成一次。
- SSE 必须自建行缓冲，`urllib` 的 `readline` 在分块边界会截断。
- assistant 的 tool_calls 消息不能改写，工具结果顺序不能乱。
- JSONL 不 flush，进程被杀丢最后一条，现象是"模型忘记刚才做过什么"，极难排查。
- 压缩后忘了跳过被替换的 message，token 原地反弹，压缩形同无效。
- Windows 下 `subprocess` 必须显式给 shell 与 cwd，别依赖当前目录。
- 事件和 entry 混用（互相写进对方的结构），json 模式立刻不可复用，一开始就别混。
